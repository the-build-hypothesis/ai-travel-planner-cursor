# AI Travel Planner
## Product Development Specification — v1.6

### Assignment

Design, implement, test, and deploy a complete AI-powered travel planning web application with guest access, registered user accounts, an administrative dashboard, and operational cost monitoring.

You are responsible for the full development lifecycle, including architecture, product design, implementation, infrastructure provisioning, quality assurance, and production deployment.

You have an **eight-hour delivery window**, measured in wall-clock time.

Your goal is to deliver a complete, reliable, visually polished application within the available time.

Make routine technical and design decisions independently. Do not wait for approval of your implementation plan.

Continue through implementation, testing, debugging, deployment, and production verification.

---

# 1. Product Overview

## 1.1 Product Name

AI Travel Planner

## 1.2 Product Vision

Build a modern AI-powered travel planning application that helps users research destinations, organize trips, and generate personalized itineraries through natural-language conversation.

The application should feel like a polished consumer SaaS product rather than a technical prototype.

Users should be able to describe the trip they want, receive personalized recommendations, refine those recommendations conversationally, and save their plans.

The application must support both guest access and registered user accounts.

A separate administrative interface must provide user management, trip inspection, API usage monitoring, and cost reporting.

## 1.3 Target Users

- Individuals planning vacations.
- Families organizing trips.
- Couples planning getaways.
- Travelers exploring unfamiliar destinations.
- Users who prefer conversational planning over traditional travel search interfaces.
- Administrators responsible for managing users and monitoring application operations.

## 1.4 Example User Journey

A user visits the application and enters:

"Plan a five-day family vacation to Tokyo in April. We have two adults and two children, ages 10 and 14. Our budget is $5,000 excluding flights. We enjoy technology, Japanese food, gaming, and cultural attractions."

The application interprets the request, asks clarifying questions when useful, and generates a personalized itinerary.

The user can subsequently request changes such as:

- "Make day three less expensive."
- "Replace the museum with something outdoors."
- "Find good restaurants near our hotel."
- "Add more activities for the kids."
- "Show me the itinerary on a map."

The application should modify the relevant portions of the trip while preserving unrelated itinerary content.

# 2. Core Functional Requirements

## 2.1 Conversational AI

Provide an interactive AI-powered conversation interface.

The assistant must:

- Understand natural-language travel requests.
- Maintain relevant conversation context.
- Ask clarifying questions when necessary.
- Generate personalized recommendations.
- Reference the current itinerary when responding.
- Modify existing plans based on user feedback.
- Preserve unrelated itinerary details when making changes.
- Distinguish verified information from estimates and suggestions.

Conversation history must remain available when a saved trip is reopened.

## 2.2 Trip Creation and Management

Allow users to create, view, edit, save, and reopen trips.

Support relevant trip information, including:

- Destination or destination preferences.
- Travel dates and duration.
- Number of travelers.
- Ages of children, when applicable.
- Budget and currency.
- Interests and activity preferences.
- Travel pace.
- Special requirements and constraints.

The application should accommodate incomplete trip requests and help users supply missing information.

## 2.3 AI Itinerary Generation

Generate structured day-by-day itineraries.

Each day should contain relevant information such as:

- Activities and attractions.
- Suggested times.
- Estimated durations.
- Locations.
- Descriptions and recommendations.
- Estimated costs, where reasonable.
- Transportation and travel considerations.

Schedules should be geographically and temporally practical.

Avoid unrealistic travel times, excessive activities, and obvious scheduling conflicts.

Itineraries must be represented as structured application data and displayed using dedicated UI components rather than only conversational text.

## 2.4 Itinerary Editing

Support itinerary modifications through conversational requests and, where appropriate, direct UI controls.

Users should be able to:

- Add activities.
- Remove activities.
- Replace activities.
- Rearrange activities.
- Change trip preferences.
- Regenerate selected portions of an itinerary.

Changes must update the underlying itinerary data and persist appropriately.

Unrelated portions of the itinerary should not be unnecessarily regenerated or discarded.

## 2.5 Destination and Attraction Research

Provide useful destination information and recommendations.

Where suitable APIs are available, retrieve information about real-world locations, including:

- Attractions.
- Restaurants.
- Points of interest.
- Geographic locations.
- Relevant travel considerations.
- Available operating-hours information.
- Estimated costs.

Do not present fabricated prices, business details, opening hours, or availability as verified facts.

Clearly identify estimates and unavailable information.

## 2.6 Interactive Maps

Provide an interactive map experience.

Users should be able to:

- View destinations.
- See itinerary locations on a map.
- Explore activities geographically.
- Identify locations associated with specific itinerary days.

Additional mapping functionality may be implemented at your discretion.

## 2.7 User Interface and Experience

Create a professional, modern, visually appealing application.

Prioritize:

- Strong visual hierarchy.
- Attractive typography.
- Consistent spacing.
- Intuitive navigation.
- Responsive desktop and mobile layouts.
- Effective loading indicators.
- Helpful empty states.
- Clear error messages.
- Accessible controls.
- Smooth interactions.
- Attractive presentation of destinations and itineraries.

The application should resemble a polished consumer SaaS product.

Avoid reducing the experience to a basic chat interface.

You have creative freedom over the visual design and interaction patterns.

# 3. Guest Access and Registered Users

## 3.1 Guest Access

Users must be able to use the travel planner without creating an account.

Guest users must be able to:

- Create trips.
- Generate itineraries.
- Modify itineraries.
- Continue conversations.
- Save and reopen trips within the same browser.

Guest data should be stored server-side using a securely generated guest identifier.

Guest identifiers must be difficult to guess and must not expose other users' trips.

## 3.2 User Registration

Provide a registration interface using email address and password.

Requirements:

1. Email addresses serve as the login identifier.
2. Email addresses must be unique, compared case-insensitively.
3. Passwords must be securely hashed using an appropriate password-hashing algorithm.
4. Passwords must never be stored or logged in plaintext.
5. Registration must validate input.
6. Registration must support email verification.
7. Newly registered users must be able to retain trips created as guests.

Use a stable internal user ID for database relationships, even though email is the login identifier.

## 3.3 User Login and Sessions

Provide secure email/password authentication.

Requirements:

- Login.
- Logout.
- Persistent sessions.
- Session expiration.
- Secure session invalidation.
- Protection against common authentication attacks.
- Appropriate rate limiting.

Use secure, HTTP-only cookies for session management.

Do not store authentication tokens in browser local storage.

## 3.4 Registered User Features

Registered users must be able to:

- View their saved trips.
- Create new trips.
- Edit existing trips.
- Reopen previous conversations.
- Access their trips from different devices.
- Update basic account information.
- Change their password.
- Log out.

All access to user-owned resources must be authorized server-side.

Users must not be able to access another user's trips by manipulating identifiers or API requests.

## 3.5 Guest-to-Account Migration

When a guest registers or logs into an existing account, provide a mechanism to associate eligible guest trips with that account.

The migration must not allow users to claim trips belonging to another guest or registered account.

Avoid duplicate trip creation during migration.

# 4. Email Verification and Password Recovery

Use **Cloudflare Email Service** for all transactional email delivery.

The sending domain has already been configured by the project administrator.

## 4.1 Email Configuration

Read the sender address from the administrator-managed runtime variable:

`EMAIL_FROM`

Use the configured Cloudflare Email Service Worker binding for sending messages.

Do not hardcode the sender address.

Do not modify the existing domain's email configuration.

## 4.2 Email Verification

After registration:

1. Generate a cryptographically secure verification token.
2. Store only a secure hash of the token.
3. Send a verification link to the registered email address.
4. Allow the user to verify ownership of the address.
5. Mark the email as verified after successful validation.
6. Invalidate the token after use.

Verification tokens must expire after a reasonable period.

Support resending verification emails with appropriate rate limiting.

## 4.3 Password Recovery

Provide a **Forgot Password?** link on the application login page.

The workflow must:

1. Accept the user's email address.
2. Generate a cryptographically secure, single-use reset token.
3. Send a password-reset link through Cloudflare Email Service.
4. Allow the user to set a new password.
5. Expire reset tokens after no more than 30 minutes.
6. Invalidate tokens after successful use.
7. Invalidate existing sessions when a password is reset.

Do not reveal whether an email address is registered.

Apply rate limiting to password-reset requests.

## 4.4 Email Delivery Failures

Handle email delivery errors gracefully.

Do not claim an email was successfully sent if the delivery operation failed.

If the email binding is unavailable, report the configuration issue without exposing sensitive details.

- Separate administrator account storage or clearly separated identity tables.
- Separate administrative sessions.
- Secure password hashing.
- Secure HTTP-only session cookies.
- Login rate limiting.
- Server-side authorization for all administrative operations.
- Session expiration and logout.

Application user accounts must not automatically receive administrative privileges.

## 5.2 Initial Administrator Account

Provide a bootstrap administrator account with:

- Username: `admin`
- Initial password: `admin`

This account is for initial setup only.

Security requirements:

1. The initial administrator must change the password before accessing administrative functionality.
2. The bootstrap account must not be usable for normal administration until its password has been changed.
3. Apply strict login rate limiting.
4. Store the initial password only as a secure password hash.
5. Do not expose administrative data before password replacement.
6. Do not automatically recreate the bootstrap administrator after it has been deleted.
7. Prevent deletion or disabling of the last active administrator.
8. Do not expose the default credentials in the public application UI.

If a secure first-use bootstrap process is needed to avoid exposing the known credentials publicly, implement one while preserving the required initial username and password.

## 5.3 Administrator Account Management

## 5.4 Application User Management

- View registration dates.
- View account status.

- Inspect a user's trips.

## 5.5 Trip Inspection

Administrators must be able to:

- View all trips.
- Sort trips by creation date and time.
- Filter and search trips.
- View trips associated with a specific user.
- View guest trips.
- Inspect itinerary details.
- Inspect trip creation and update timestamps.
- View API usage and cost associated with each trip.

Provide pagination for large datasets.

Each usage record should contain, where applicable:

- Timestamp.
- Provider.
- Model or API endpoint.
- Operation type.
- Associated user or guest.
- Associated trip.
- Request status.
- Input tokens.
- Output tokens.
- Billable request count or units.
- Estimated cost.
- Currency.
- Pricing reference or version.
- Request duration.
- Relevant error information.

Never store API credentials in usage records.

## 6.6 LLM Cost Tracking

Track LLM usage using provider-reported token counts when available.

Calculate estimated costs using applicable model pricing.

Requirements:

- Support model-specific pricing.
- Distinguish input and output token costs.
- Account for additional billable token categories where relevant.
- Preserve the pricing assumptions used for historical calculations.
- Associate costs with users, guests, and trips where possible.
- Track LLM calls that occur outside a saved trip.

## 6.7 Google Places API Cost Tracking

Track Google Places API usage and estimated costs.

Requirements:

- Identify the relevant API endpoint or billing SKU.
- Track billable request counts or units.
- Use appropriate configurable pricing assumptions.
- Associate costs with users, guests, and trips.
- Track requests that occur outside saved trips.
- Avoid treating every Google API request as having the same cost.

## 6.8 Cost Accuracy

Dashboard costs represent application-level estimates unless reconciled with authoritative billing data.

Do not present estimated costs as exact invoices.

Preserve enough information to explain how costs were calculated.

The sum of per-trip costs may differ from overall costs because some API activity may not be attributable to a saved trip.

Provide a way to account for unattributed usage.

## 6.9 Monitoring Visualizations

Provide useful visualizations, including:

- API cost over time.
- Trip creation over time.
- User registrations over time.
- LLM usage over time.
- Google Places usage over time.

Use the selected date range consistently.

## 6.10 Operational Monitoring

Track relevant application errors and API failures.

Where practical, expose:

- Failed LLM requests.
- Failed Google Places requests.
- API response latency.
- Recent application errors.
- Request volume.

Avoid collecting unnecessary sensitive information.
